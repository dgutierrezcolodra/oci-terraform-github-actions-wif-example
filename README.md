# OCI Workload Identity Federation references for GitHub Actions

*Technical example current on 27 July 2026*

CI pipelines often authenticate to OCI with a user API private key stored as a
long-lived repository secret. These references replace that user credential
with a GitHub OIDC identity mapped to an exact repository and branch. The OCI
Terraform provider exchanges the short-lived GitHub JWT, creates its own
ephemeral signing key, and renews its OCI session without exposing an OCI user
API key to the workflow.

This is not a secretless design: the runtime token-exchange application still
uses a narrowly scoped OAuth client ID and secret. It removes the OCI user API
key, fingerprint, user OCID, and long-lived signing key from CI.

| | API-key workflow | This WIF reference |
|---|---|---|
| Workload identity | OCI user | Exact GitHub repository and branch subject |
| OCI request key | Long-lived private key stored in CI | Ephemeral key generated by the OCI provider |
| OCI session | User API-key authentication | Short-lived UPST owned and renewed by the provider |
| GitHub secrets | Tenancy, user, fingerprint, and private key | Dedicated token-exchange client and workload settings |
| Revocation | Disable or delete the user API key | Disable the OAuth application or remove the exact trust mapping |

Generic `WorkloadIdentityFederation` authentication became available in OCI
Terraform provider 8.22.0. This repository requires, locks, and validates
provider 8.24.0 as its validated baseline.

## When to use this pattern

Prefer the identity native to the runner's OCI runtime when one is available:

| Runner location | Preferred OCI authentication |
|---|---|
| OCI Compute instance | [Instance Principals](https://docs.oracle.com/en-us/iaas/Content/Identity/Tasks/callingservicesfrominstances.htm) |
| Pod in an enhanced OKE cluster | [OKE Workload Identity](https://docs.oracle.com/en-us/iaas/Content/ContEng/Tasks/contenggrantingworkloadaccesstoresources.htm) |
| GitHub-hosted runner or self-hosted runner outside OCI | Generic WIF from this repository |

This repository is the secure alternative to an OCI user API key when the
runner cannot use Instance Principals or OKE Workload Identity. It lets the
external runner present its own short-lived GitHub identity instead of storing
an OCI user's signing key.

## Authentication flow

```mermaid
sequenceDiagram
    participant Job as GitHub Actions job
    participant GitHub as GitHub OIDC
    participant Provider as OCI Terraform provider 8.24.0
    participant Domain as OCI Identity Domain
    participant OCI as OCI APIs

    Job->>GitHub: Request JWT for https://cloud.oracle.com
    GitHub-->>Job: Short-lived JWT written below RUNNER_TEMP
    Job->>Provider: Pass protected JWT file path
    Provider->>Provider: Generate ephemeral RSA key
    Provider->>Domain: Exchange JWT and public key
    Domain-->>Provider: Short-lived OCI UPST
    Provider->>OCI: Sign API requests with matching private key
    Note over Job,Provider: Extended workflow refreshes only the source JWT file
    Provider->>Domain: Renew UPST and key together when required
```

Terraform owns the OCI UPST and its proof-of-possession key. The extended
workflow refreshes only the source GitHub JWT; it never creates or replaces OCI
credentials outside the provider.

provider WIF; the Ansible adapter exists because the `oracle.oci` collection
does not consume that provider configuration.

## Validated Terraform baseline

The generic WIF capability was [introduced in provider
8.22.0](https://github.com/oracle/terraform-provider-oci/blob/v8.22.0/CHANGELOG.md).
This reference keeps 8.24.0 as its minimum because that is the version
validated end to end across the standard and extended Terraform workflows and
recorded in both dependency lock files. With that validated baseline, the
provider performs the native flow:

1. Terraform reads the GitHub OIDC JWT from a protected file.
2. The provider generates an ephemeral RSA key pair.
3. The provider exchanges the JWT for an OCI UPST.
4. The provider signs OCI API requests with the matching private key.
5. The provider renews the UPST and key together when required.

The shared one-shot action uses official
`actions/github-script@3a2844b7e9c422d3c10d287c895573f7108da1b3` (`v9.0.0`)
to obtain the GitHub JWT. It writes the JWT atomically below `RUNNER_TEMP`,
exports only its path, and never creates OCI credentials.

```yaml
- name: Create GitHub OIDC token file
  uses: ./.github/actions/github-oidc-token
  with:
    audience: https://cloud.oracle.com
```

## Prerequisites and GitHub configuration

Complete the one-time OCI configuration in [SETUP.md](./SETUP.md). You need an
OCI Identity Domain service user and least-privilege IAM policy, a dedicated
confidential token-exchange application, one active trust with exact audience
and subject restrictions, and `id-token: write` for the GitHub job.

Create these repository Actions secrets:

| Secret | Purpose |
|---|---|
| `CLIENT_ID` | Client ID of the OCI token-exchange application |
| `CLIENT_SECRET` | Client secret of the OCI token-exchange application |
| `DOMAIN_BASE_URL` | OCI Identity Domain URL |
| `OCI_REGION` | OCI region, for example `eu-madrid-1` |
| `COMPARTMENT_ID` | Target compartment OCID |

The checked-in workflows and trust example use the default subject
`repo:<owner>/<repository>:ref:refs/heads/main`. When copying the reference,
replace the owner and repository and, if necessary, replace `main` consistently
with your protected deployment branch. Do not broaden the subject. A job-level
GitHub environment or OIDC subject customization changes the `sub` claim and
will not match the documented rule.

`apply-and-destroy` is an explicit manual choice and reads the compartment only
from the fixed repository secret. A workflow input cannot redirect an apply to
another compartment.

## Terraform configuration

```hcl
terraform {
  required_providers {
    oci = {
      source  = "oracle/oci"
      version = ">= 8.24.0, < 9.0.0"
    }
  }
}

provider "oci" {
  auth   = "WorkloadIdentityFederation"
  region = var.oci_region
}
```

The workflows supply the remaining configuration through environment
variables:

```text
OCI_WORKLOAD_IDENTITY_TOKEN_PATH
OCI_TOKEN_EXCHANGE_DOMAIN_URL
OCI_TOKEN_EXCHANGE_AUTH=OAuthClientCredentials
OCI_TOKEN_EXCHANGE_CLIENT_ID
OCI_TOKEN_EXCHANGE_CLIENT_SECRET
OCI_TOKEN_EXCHANGE_REQUESTED_TOKEN_TYPE=urn:oci:token-type:oci-upst
OCI_TOKEN_EXCHANGE_SUBJECT_TOKEN_TYPE=jwt
```

`CLIENT_SECRET` is passed only to the Terraform steps that call the configured
provider. It is masked and is not persisted through `GITHUB_ENV`.

## Run the standard Terraform example

1. Fork or copy the repository and complete [SETUP.md](./SETUP.md).
2. Add the repository secrets listed above.
3. Run **Demo Terraform Apply (Standard)** from the branch in the trust.
4. Select `plan` first.
5. Optionally select `apply-and-destroy` to create one private validation bucket
   and remove it in the same job.

The example keeps Terraform state local to the job. Configure a remote backend
before adapting it to persistent infrastructure.

The automatic `push` trigger is limited to the standard Terraform example, its
OIDC action, and its own workflow file. Changes to Ansible or the extended
examples do not start a real OCI Terraform plan.

## Extended Terraform operations

The provider can renew its OCI UPST but cannot call GitHub to replace an
expired source JWT. The extended workflow replaces only that source file:

```yaml
- name: Create refreshable GitHub OIDC token file
  uses: ./.github/actions/github-oidc-token-refresh
  with:
    audience: https://cloud.oracle.com
    refresh_interval_minutes: 1
```

The provider rereads the file for its next exchange and continues to own the
UPST and key. GitHub OIDC JWTs have an observed lifetime of roughly five
minutes; GitHub does not document that lifetime as a guarantee. The action
therefore accepts only one- through four-minute refresh intervals.

**Demo Terraform Token Refresh** defaults to a 120-second smoke test and fails
unless the source-JWT file modification time strictly increases. Set
`wait_duration` to `65m` only for the opt-in full UPST-renewal proof.

## Ansible adapter

The `oracle.oci` collection does not consume the Terraform provider's native WIF
configuration. `.github/actions/ansible-oci-wif` uses the OCI Python SDK to
create a short-lived security token, matching ephemeral private key, and OCI
config below `RUNNER_TEMP`. These files exist only for the current job and are
removed by always-run cleanup. No OCI user API key is used.

`oracle.oci` 5.6.0 is not published to Ansible Galaxy. The shared
`examples/ansible/requirements.yml` therefore pins Oracle's source tag to an
exact Git commit. Installing it requires `git` on the runner and does not use
Galaxy collection-signature verification; review and update the pinned commit
deliberately.

**Demo Ansible WIF Namespace Validation** performs one manual, read-only Object
Storage namespace check.

For the extended example, the playbook waits, calls the adapter again between
tasks, and replaces the OCI security token and matching key together. Later
module tasks read the new files. An already-running module keeps its in-memory
signer and cannot be refreshed by replacing files. For a long OCI operation,
submit it asynchronously with `wait: false`, renew after that task returns, and
poll with later facts or status tasks. The 65-minute proof remains manual and
opt-in and distributes no credentials to managed hosts.

## Security properties

- The trust matches the exact GitHub issuer, audience, repository, and branch.
- `sub eq *` is never acceptable for this pattern.
- The runtime OAuth application has no Identity Domain administrator role.
- Credential directories use mode `0700`; token, key, and config files are
  written atomically with mode `0600`.
- Credential material stays below `RUNNER_TEMP` and is deleted by job cleanup.
- Workflows never print or upload JWTs, OCI UPSTs, private keys, client secrets,
  Terraform state, or credential files.
- Terraform alone owns its OCI UPST and proof-of-possession key.
- The service user receives only the OCI permissions required by the copied
  workload.
